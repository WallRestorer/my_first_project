# Ответы на вопросы

## 1. Три основные области работы с файлами в Git

- **Рабочая папка (Working Directory)** — здесь вы редактируете файлы. Это ваши текущие файлы на диске.
- **Индекс (Staging Area)** — промежуточная область, куда попадают файлы после `git add`. Здесь подготавливается будущий коммит.
- **Репозиторий (Repository)** — хранилище всех закоммиченных версий файлов (папка `.git`).

**Отличия:** рабочая папка — черновик, индекс — «корзина для коммита», репозиторий — архив всех сохранённых версий.

## 2. Что происходит при выполнении команд

- **git add** — добавляет изменения файлов в индекс (staging area). Файл подготавливается к коммиту.
- **git commit** — сохраняет содержимое индекса в репозиторий как новую версию (коммит) с уникальным хешем и сообщением.
- **git push** — отправляет локальные коммиты на удалённый репозиторий (например, на GitHub).

## 3. Почему важно писать информативные сообщения к коммитам

Информативные сообщения помогают:
- Понять историю изменений без просмотра кода.
- Быстро найти нужный коммит (например, когда появился баг).
- Работать в команде: коллеги понимают, что было сделано.
- Откатывать изменения осознанно.

Сообщения вида «update» или «исправление» бесполезны — по ним нельзя понять суть изменений.

## 4. Чем отличается `git add имя_файла` от `git add .`

- `git add имя_файла` — добавляет в индекс только конкретный файл.
- `git add .` — добавляет **все** изменённые и новые файлы из текущей директории (рекурсивно).

**Когда что использовать:**
- `git add имя_файла` — когда нужно закоммитить только часть изменений.
- `git add .` — когда нужно закоммитить всё сразу (удобно, но требует осторожности, чтобы не добавить лишнее).

## 5. Что показывает `git status` и как меняется её вывод

`git status` показывает состояние рабочей папки и индекса:
- Какие файлы изменены, но ещё не в индексе.
- Какие файлы добавлены в индекс (готовы к коммиту).
- Какие файлы не отслеживаются (untracked).
- В какой ветке вы находитесь.

**Как меняется вывод:**
- После `git init` — «No commits yet».
- После создания файла — «Untracked files».
- После `git add` — «Changes to be committed».
- После `git commit` — «nothing to commit, working tree clean».

## 6. Для чего нужна `git remote add origin URL` и что означает «origin»

- Команда **связывает** локальный репозиторий с удалённым по указанному URL.
- **origin** — это стандартное (условное) имя для удалённого репозитория. Можно назвать иначе, но `origin` — общепринятое соглашение.

## 7. Зачем нужен флаг `-u` в `git push -u origin main`

Флаг `-u` (или `--set-upstream`) **запоминает**, что локальная ветка `main` связана с удалённой `origin/main`. После этого можно писать просто `git push` или `git pull` без указания ветки и remote.

## 8. Что такое ветка по умолчанию и какая создалась у вас

**Ветка по умолчанию** — основная ветка, в которой ведётся разработка. Исторически она называлась `master`, но с 2020 года GitHub использует `main`.

У меня создалась ветка: **main** (по умолчанию в GitHub).

**Почему это важно:** ветка по умолчанию — та, куда попадают изменения по умолчанию; от неё создаются другие ветки; на неё настроены CI/CD и деплой.

## 9. Как просмотреть историю коммитов

- Через терминал: `git log` (подробно) или `git log --oneline` (кратко).
- Через GitHub: вкладка **Commits** на странице репозитория.

**Что видно о каждом коммите:**
- Хеш (уникальный идентификатор)
- Автор
- Дата и время
- Сообщение коммита
- Изменённые файлы (по клику)

## 10. Что произойдёт, если изменить файл, но не выполнить `git add` перед `git commit`

Изменения **не попадут в коммит**. Git закоммитит только то, что находится в индексе (staging area). Изменённый файл останется в рабочей папке как «не проиндексированный» и будет отображаться в `git status` как «Changes not staged for commit».

Чтобы изменения попали в коммит, нужно сначала выполнить `git add`.
